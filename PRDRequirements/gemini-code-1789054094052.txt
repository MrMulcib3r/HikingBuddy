## 1. Executive One-Pager
*   **The Problem:** Ultralight thru-hikers obsess over every gram of their gear, but tracking base weight across multiple hikes is a data-management nightmare. Updating a single item's weight in a global "gear closet" often retroactively corrupts older historical hike lists. Furthermore, hikers often need to check lists at trailheads without internet access.
*   **The Solution:** **HikingBuddy**, an open-source, mobile-first Progressive Web App (PWA) that allows users to manage a personal gear database, assemble customized packing lists, and freeze them into immutable, shareable "snapshots" that survive future gear edits. 
*   **Scope:** Personal gear database (CRUD), dynamic list building, snapshot versioning, public URL sharing, offline-first PWA architecture, and category-based weight analytics (pie charts).
*   **Target Audience:** Ultralight thru-hikers, backpackers, and gear enthusiasts.
*   **Launch Date:** TBD (Open-Source Community Driven).

---

## 2. Overview & Context
For ultralight hikers, the difference between a successful 2,600-mile hike and an agonizing failure often comes down to pack weight. Hikers manage a "Gear Closet" (everything they own) and compile "Lists" (what they take on a specific trip). 

Currently, if a hiker buys a new, lighter tent fly, they update their "Tent" entry in their database. However, in poorly architected systems, this retroactively alters the weight of their historical "Appalachian Trail 2024" list, destroying their historical records. HikingBuddy addresses this with a **Snapshot Architecture**, allowing historical lists to be frozen in time, shared publicly (e.g., "PCT 2025 Gear List"), and accessed offline via a PWA while deep in the backcountry.

## 3. Customer Insights & Evidence
*   **Primary Quote:** *"I updated the weight of my sleeping pad because I trimmed it, and suddenly my LighterPack list from three years ago says I carried 8 lbs instead of 8.5 lbs. My historical data is ruined."* — Anonymous Thru-Hiker
*   **Secondary Context:** Thru-hikers frequently perform "shakedowns" at trailheads, dropping gear before starting. A lack of cell service means cloud-only apps are useless at the exact moment a hiker needs to consult their final pack list.

## 4. Goals & Non-Goals
**Goals:**
*	Provide a place where hikers can create and manage their gear and use it to create and manage gear lists for their hikes.
*   Provide a fast, easy to read and data-dense interface for managing a personal gear inventory.
*   Prevent historical data corruption via immutable list snapshots.
*   Enable offline availability (read and write) via PWA architecture.
*   Allow easy public sharing of specific hike snapshots.

**Non-Goals:**
*   Creating a global, crowd-sourced gear database (each user manages their own gear).
*   E-commerce integrations or affiliate link monetization.
*   Social networking features (comments, likes on lists).
*   Native iOS/Android App Store distribution (PWA is sufficient).

---

## 5. Alternatives Considered
*   **LighterPack:** The current community standard. *Rejected* because it lacks true offline PWA support, has an aging UI, and does not natively support immutable version snapshots in a clean way.
*   **Spreadsheets (Excel/Google Sheets):** Highly customizable. *Rejected* because they offer a terrible mobile experience, break easily, and are difficult to share aesthetically.
*   **Notion/Obsidian:** Great offline (Obsidian). *Rejected* because they lack built-in weight analytics and conversion calculations.

## 7. Requirements

### Functional Requirements (FR)
*   **FR-1. Authentication:** Users must be able to create an account and log in securely to access their personal gear database.
*   **FR-2. Gear Inventory (CRUD):** Users must be able to Create, Read, Update, and Delete items. Items must have the following properties: Name, Category, Description, Weight, and Default Quantity.
*   **FR-3. Unit Preferences:** Users must be able to toggle global display units between Metric (grams/kg) and Imperial (ounces/lbs). The system must store the absolute weight (e.g., in grams) and convert on the fly.
*   **FR-4. List Management:** Users must be able to create named lists, assign gear items from their inventory, and override the quantity of an item specifically for that list.
*   **FR-5. Weight Analytics:** Every list must dynamically display a pie chart visualizing total weight distributed by "Category".
*   **FR-6. Immutable Snapshots (Core Feature):** Users must be able to trigger a "Save Snapshot" action on a list. This creates an immutable version of the list where the item properties (weight, name, description) are hard-copied. Subsequent changes to the core gear inventory *must not* affect this snapshot.
*   **FR-7. Public Sharing:** Users must be able to generate a unique, publicly accessible URL for any saved snapshot. The public view is read-only.

### Non-Functional Requirements (NFR)
*   **NFR-1. Offline Capability (PWA):** The app must install as a PWA. Gear and lists must be cached locally (e.g., IndexedDB) allowing full read/write access offline, syncing to the server when connection is restored.
*   **NFR-2. Open Source:** The codebase must be licensed under an open-source license (e.g., MIT) and easily self-hostable via Docker.
*   **NFR-3. Mobile-First UI:** The interface must prioritize mobile viewports, as hikers mostly use smartphones on the trail.

### Acceptance Criteria (Gherkin)
*   *Scenario: Editing gear does not ruin a snapshot*
    *   **Given** I have a saved Snapshot of "AT 2025" containing a "Tent" weighing 800g
    *   **When** I edit the "Tent" in my main Gear Closet to weigh 750g
    *   **Then** my "AT 2025" snapshot must still show the tent weighing 800g
    *   **And** any *new* list I create will show the tent weighing 750g.

## 8. UX & Design Considerations
*   **Information Density:** Ultralight hikers tolerate high information density. Lists should resemble clean, highly legible data tables.
*   **Sticky Header:** When scrolling through a long packing list on mobile, the "Total Weight" and "Pie Chart Toggle" should remain sticky at the top or bottom of the screen.
*   **Accessibility:** WCAG 2.1 AA compliance required. High contrast mode for bright sunlight outdoors.

---

## 9. Technical Notes
*   **Architecture:** Local-first architecture is heavily recommended to meet NFR-1. Tools like **RxDB, WatermelonDB, or ElectricSQL** should be considered for local device storage that auto-syncs with a remote database (e.g., Postgres/Supabase).
*   **Snapshot Schema:** Do *not* use relational foreign keys (Item ID) for snapshots. Snapshots must serialize and embed the item data (JSONB or separate snapshot_items table) to sever the link to the mutable master item.
*   **Floating Point Math:** Weight conversions (oz to grams) must handle floating-point math safely to avoid rounding errors (e.g., storing all weights internally as integers representing milligrams).

---

## 10. Metrics & Success Criteria
*   **Metric 1: Offline Sync Success Rate.** Target: 99% of offline edits successfully merge when returning online without data loss.
*   **Metric 2: Snapshot Creation Rate.** Target: 70% of active users create at least one snapshot, proving feature adoption.
*   **Metric 3: Public Shares.** Measure the number of unique snapshot URLs accessed by non-authenticated users.

---

## 11. Risks & Mitigations
| Risk | Severity | Mitigation |
| :--- | :--- | :--- |
| **Sync Conflicts** (Editing gear on two offline devices simultaneously) | High | Implement "Last-Write-Wins" logic based on timestamp. As an open-source tool, complex CRDTs might be over-engineering for v1, but warn the user if a conflict occurs. |
| **Data Bloat** (Saving too many heavy JSON snapshots) | Low | Text data is cheap. Implement standard payload limits. |
| **PWA Cache Eviction** (iOS deleting local data if storage is full) | Medium | Prompt users to use the "Add to Homescreen" feature, which generally protects Safari IndexedDB data from routine eviction. |

---

## 12. Rollout Plan
*   **Phase 1 (Alpha):** Local-only PWA. No server sync. Users test the UI, weight conversions, and pie charts.
*   **Phase 2 (Beta):** Implement user auth, backend database, and the offline-to-online sync engine. 
*   **Phase 3 (GA):** Implement URL sharing and open-source the repository with Docker setup instructions.

## 15. Open Questions & Assumptions
*   **Assumption:** Users will accept "Last-Write-Wins" for syncing conflicts rather than needing a complex manual merge UI.
*   **Open Question:** Should categories be pre-defined globally (e.g., Shelter, Sleep System, Consumables) or entirely user-generated? *(Recommendation: Provide a default list that users can edit/delete).*
*   **Open Question:** How will the open-source community fund the central database hosting for non-self-hosting users?

## 16. Glossary
*   **Base Weight:** The weight of a loaded backpack, excluding "Consumables" (food, water, fuel) and "Worn Weight" (clothes currently on the body).
*   **Thru-Hiker:** A hiker traversing a long-distance trail (e.g., PCT, AT) from end to end in a single trip.
*   **Shakedown:** The process of reviewing a gear list (often publicly) to find ways to reduce weight.
*   **PWA:** Progressive Web App. A website that looks and behaves like a mobile app and can work offline.
